# Controlled automatic Terra run — readiness review

6 November 2026. This review makes no paid request and does not create or activate an approval. Existing live state and retained historical failure evidence are preserved.

## Audit and narrow corrections

1. **Same live contracts and execution:** The private route constructs PrivateStudioService with its real default LiveDesigner factory. The Node instrumentation worker constructs that same service. Both use advancePromptRun → runStagedGeneration → existing programme solver/compiler. The offline SDK tests replace only provider HTTP responses. There is no live import of PromptMockDesigner, fixture selection or developer-authored house substitution.
2. **Evidence before processing:** Exact system/prompt is persisted before dispatch. The complete header-free provider response body and request body are now durably captured before SDK parsing; previously an invalid provider envelope could escape raw-body retention. Parsed raw output, available provider usage/request ID/finish reason are persisted before structured output access. A new checkpoint hook persists accepted/rejected validation findings, full stage input, solver construction results and exception details before completion/save processing. Outer execution exceptions retain message and stack. If the provider omits usage or an invalid envelope prevents trustworthy interpretation, the original response is retained and accounting is explicitly uncertain; missing metadata is not invented.
3. **Automatic progression and duplicates:** Browser Generate issues only start with automatic:true. A durable owned project admits one run and consumes one exact-brief authorization. The server worker alone advances it, with an atomic reservation and stage revision. Repeated clicks, competing workers, refreshes and transport errors cannot reuse a reservation. No automatic paid retry occurs. A browser refresh reads the owned run; it never replays the provider call. The worker is local-development Node infrastructure, not a production/serverless service.
4. **Architectural handoffs:** Every request carries the original brief and accepted decision slices. Stage 3 receives fixed block dimensions, coordinates, adjacency, stacking and open spaces. Stages 4–5 receive actual solved room geometry and measured exterior walls; Stage 5 also receives fixed building/entrance/veranda reservations. Prior roof/exterior decisions are retained in accepted slices. Each deterministic stage applies its own slice to the prior authoritative spec, preserving earlier block/room/interior identities. Incomplete or unknown component maps fail rather than silently accepting placeholders.
5. **Progress:** Added the previously missing durable validating phase. Running means dispatch/provider work; validating means a response has been retained and is being interpreted/constructed/validated/saved. Completed requires an accepted checkpoint. Failed and uncertain retain distinct visible states and the attempted stage, separate from accepted count. Cancellation remains available during running and validating. A rapid validation may finish between browser polls; no artificial progress delay is introduced.
6. **Failure preservation:** The prior accepted source/scene remains authoritative on rejection. All failed/uncertain jobs stop before another provider reservation. Cancellation allows an already active request to settle and save, then blocks future stages. Unknown requests and interrupted running work are never automatically redispatched.
7. **Unchanged spending controls:** At most five calls, maxRetries:0, maxCorrectionsPerStage:0, 12,000 output tokens/call, 170-second timeout/call, US$1.40 maximum under the existing configured price policy. Each conservative reservation is US$0.275072; five are US$1.375360. The server checks cumulative actual/held spending before every reservation. The provider adapter permits one outbound dispatch per reservation and checks model, wire size and output limit. Unexpected usage or an exceeded reservation stops as uncertain. Provider billing reconciliation is not proved by mocked usage.
8. **Approval preparation only:** [approval-draft.json](approval-draft.json) contains the exact genuinely new Mediterranean garden-house prompt, brief/policy hashes, automatic mode and limits. It has no approval ID or bound project and is not in the approval store. Read-only inspection found no unresolved runs and no unused approvals. Before activation, bind it to exactly one new owned project with no run and obtain explicit user approval of the exact prompt and US$1.40 maximum.

## Initiating the experiment after explicit approval

1. Start the existing development app with `npm run dev -- --port 3015`, keeping its Node server running. The worker starts automatically. A production build/start does not enable this private development-only flow.
2. Open a direct-scene project in Studio at `http://localhost:3015` and sign in to private Studio using the existing Studio password. Do not reuse or restart a historical run.
3. Click **Create owned server project**, then copy the exact approved prompt from the draft into **Live architectural description**. This setup does not call Terra.
4. Only after explicit approval of the exact prompt/budget, record one project-bound single-use approval through the existing administrator approval function. Do not call that function now. Reload Studio if necessary and select the new server project; it must show that the description/project matches the unused approval.
5. Click **Generate House** once. Watch the five automatic stages and actual recorded/held spending. No advance buttons or extra authorization are required between successful stages. A refresh is safe; select the same server project to recover its status.
6. On completion, Studio displays the house and imports its editable source if the local project baseline is unchanged. The completed server save is retained. If it stops failed or uncertain, inspect its saved checkpoint/evidence; do not initiate another run or correction call without separate authorization.

## Limits of this assessment

This is approval readiness for one controlled local experiment, not proof that Terra will produce a complete or attractive house in five responses. No live model availability, live latency, provider-account billing, real architectural quality or new live prompt fidelity has been tested. The original missing Stage 2 response remains unknowable. Power loss during the short file-store transaction can still leave a fail-closed stale lock requiring operator review; the system does not steal locks or risk duplicate billing. No production database or deployment change is needed for this local experiment.
