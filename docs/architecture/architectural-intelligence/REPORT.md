# Architectural intelligence, research preparation and scale — 28 October 2026

Implemented and verified offline. **Zero real OpenAI requests, zero paid research/review/revision calls, no key changes, no production knowledge writes, no migrations, commits or deployment.** Existing dirty/untracked work was retained. Mocked provider invocations in route tests are not real API calls. Browser tests used an isolated profile and blocked every `/api/` and external request.

The result improves the information and architectural responsibilities in normal Generate. It does **not** establish that Terra now autonomously produces beautiful, complete luxury estates. That requires a later expressly authorized live generation and review of actual geometry.

1. **What prevented Playground ideas being used at larger scales?** There is no whole-residence 300 m² cap in the direct-scene executor. Individual residential-wing assemblies are bounded to 40 × 30 m, but multiple differentiated buildings and primitive-authored levels are possible. The gap was transferring architectural relationships from hand-authored renderer examples into normal Generate, while keeping room, opening and threshold proportions. The original TropicalVilla source and retained [Solana view](../code-driven/original-solana-overview.png) show primary/subordinate volumes, an articulated arrival portal, recessed upper accommodation, layered roofs/soffits, local screens and coordinated terraces/water. New guidance explicitly transfers those principles without copying coordinates, dimensions or layouts. The unchanged 400-element/800-operation budgets and construction coordination burden still limit detailed estate scale.

2. **Does Terra understand property value versus construction cost?** Previously the nine recipes explicitly described “property-value or budget context”, and the parser used the first currency amount regardless of its role. The parser now distinguishes labelled property/market value, construction budget, land value and unspecified budget. A construction-only or land-only amount no longer selects a property-value recipe. Multiple amounts are retained separately. All nine recipe definitions retain their qualitative bands (approximately $100k through $100m+) and now distinguish market value from construction spend. Bare `$` carries an explicit USD assumption; recognized other dollar currencies are not silently converted. Large value-only briefs receive estate-relevant retrieval without mandated dimensions, storeys or amenities; explicit compact constraints prevail. Runtime guidance also explains land/location premiums, craftsmanship, household programme and uncertain regional costs. This is bounded linguistic parsing and design guidance, not a general financial interpreter, valuation model or construction-cost estimator. No precise local market facts were invented.

   Existing stored revisions can override seed definitions, and were deliberately not rewritten. The independent value/cost guidance is therefore added to the actual Generate/broad-development context regardless of which stored recipe revision is selected. The retained snapshot has existing version-2 property records; their history remains intact.

3. **What existing knowledge was underused?** Primary/secondary hierarchy, arrival sequence, living/view relationships, climate-specific facade depth, roof/outdoor relationships, regional material durability, existing approved legacy recipes and reviewed design lessons all share the existing retrieval path. Merely having 334 approved records did not mean they all informed a request or translated into geometry. The retained snapshot still yields **334 approved active records**. The new estate request selects eight within the unchanged 18,000-character retrieval budget, with reasons and exclusions recorded. Knowledge records now carry source provenance into the model context rather than dropping it during serialization. Legacy parameter dimensions remain options rather than templates. No new seed catalogue or duplicate knowledge database was introduced.

4. **Can the OpenAI integration support safe web research?** Official [web-search documentation](https://developers.openai.com/api/docs/guides/tools-web-search) documents Responses web search, source annotations, domain filtering and search charges. The installed `@ai-sdk/openai` exposes `responses()` and `tools.webSearch()`. Official [structured-output documentation](https://developers.openai.com/api/docs/guides/structured-outputs) documents schema-based responses. These establish API/SDK facilities; they do not prove that the configured Terra model/account supports the exact combined search-plus-construction schema. That combination was not exercised. Construction output schema, retries, validation and executor were not relaxed. A separate preparation/intake boundary avoids attaching search tools to construction until compatibility and an explicit cost allowance can be checked.

5. **What research capability was implemented?** Offline, knowledge-first research preparation and cited finding intake, **not live autonomous web search**. The existing Learn control center now includes “Architectural research · offline preparation”, with off / on-request / when-needed preparation policies, an optional uncertainty field, query preview, a cited shading example, proposal preview and an explicit save-unapproved action. Policies govern preparation, not paid searches or future automatic Generate requests. The normal Generate trace also records the preparation assessment and explicitly says no external search was performed.

   `POST /api/admin/library/architecture/research` uses the existing admin access check. `prepare` reads approved knowledge and returns at most two proposed queries; `preview` validates up to four findings with up to three sources each; `propose` imports only proposed records through the existing optimistic revision service. There is no provider import, HTTP fetch, crawler, scheduler, retry loop or execution action in this endpoint. Missing composition/regional/style coverage and explicit uncertainty are heuristics; they do not reliably detect every unfamiliar style or locality. No blanket claim of intelligent unknown-topic detection is made.

   A developer-prepared example interprets the professional [Your Home shading guide](https://www.yourhome.gov.au/passive-design/shading), read on 28 October 2026. It links shade to orientation, openings and climate, and explicitly warns against transferring Australian orientation rules to Caribbean sites. The proposed record retains the URL, research date, evidence basis, applicability, spatial relationships, supported primitive methods and full limitations. Publication date is unknown. This is a human/developer-prepared interpretation, not autonomous Terra research or an approved source-derived lesson. The example has **not** been written to the user's knowledge store.

6. **What can Terra learn automatically, and what needs approval?** Current retrieval uses approved knowledge first. The existing visual-learning workflow can retain candidate lessons and geometric/visual evidence; its approval rules remain unchanged. Research can be prepared and findings normalized into proposals, but this implementation does not autonomously search or synthesize findings. Intake rejects caller-supplied approval, review, verified flags and scene operations. Proposed findings are excluded from Generate. Approval requires a separate existing knowledge revision with review and verified provenance; validation of a URL alone is not verification. Tests simulate that reviewer transition in disposable temporary files only. No live records were approved, retired or superseded.

7. **How does one system produce different concepts?** Within the existing paid Generate response, guidance now asks Terra to compare plausible organizations, choose one in `volumeHierarchy` with a concept name/reason, and retain principal relationships using existing `spatialRelationships` and construction IDs. Identity, programme, views/site assumptions, arrival and roof/facade/outdoor decisions must translate into the same atomic operation transaction. There is no new planner, preset selector or geometry writer. Variation comes from section, adjacency, courtyard/wing distribution and circulation, not random finishes. Rerun diversity and reproducibility of a new autonomous design remain unverified; the stored chosen plan/geometry provide coherence for subsequent edits.

   Two **developer-authored exterior construction studies** demonstrate representation through the existing executor for the same broad tropical waterfront brief:

   | Study | Wing floor surfaces | Elements | Organization |

   | Garden court | 1,896 m² | 69 | Taller main living block, opposing private wings and a guest block around an outdoor room |

   These totals sum wing slab surfaces, not certified enclosed/net usable area. Studies use ordinary `assemble`/`add` operations and preserve individually editable parts. They have no internal suite partitions or covered circulation and intentionally disclose those omissions. Their sparse, repetitive envelopes do **not** achieve the sophistication of the original Playground house; passing validation is not proof of architectural beauty. They are fixtures only and are never supplied as production design templates.

8. **Which construction limits still affect quality?** One rectangular opening per wall segment; only rectangular solids plus the approved version-pinned pavilion; flat/gable/hip roofs; no arbitrary curved/polygonal roof, mesh or CSG authoring; a limited material/furnishing vocabulary; no automatic shared-wall/roof junctions; one-storey residential-wing assemblies without room partitions, side/rear passage design or stairs; manual stair/void/landing construction; no certified navigation, engineering, services or climate simulation. New Generate still stages flat sites. A large detailed programme can exhaust the unchanged element/output budgets. Roof, opening, enclosure, pool, circulation and support coordination remain actual design work. Original Playground renderer richness is not automatically an executable assembly capability.

9. **What changes should improve first-pass design?** Normal homepage Generate now receives explicit Playground principles, nonuniform scaling guidance, same-response concept selection, separate monetary roles, approved knowledge with provenance, existing reviewed lessons and the mechanically derived capability contract. Site/view and programme assumptions must be disclosed; selected identity and relationships must become editable operations. The actual HTTP handler test captures this complete request using the shared homepage request builder and unchanged executor. It replays an unchanged retained response to prove wiring, not to claim the new instructions influenced that geometry. Explicit Redesign/Complete receive the same broad design guidance; Refine retains its existing scope.

10. **What remains unverified until live generation?** Whether Terra follows the strengthened responsibilities, chooses genuinely original concepts across reruns, delivers an appropriate complete programme, preserves architectural proportions at estate scale, uses citations correctly and produces a beautiful, coordinated first pass within the output/geometry budgets. No live model/search compatibility, latency, token usage, research quality, account access, new market references or autonomous improvement was measured. These are remaining validations, not inferred successes from the tests.
