# Private development live-execution gate — specified, not activated

No paid endpoint is enabled by this work. This is the smallest proposed secure server path, not a claim that the current application has authenticated users or enforceable billing. No migration was run.

## Inspected infrastructure

- `src/lib/admin/auth.ts` compares the caller-supplied `x-admin-email` with a configured email. `AdminGate` is a UI gate. Neither establishes identity. They must never admit paid work.
- `useProjectStore`, `projectStorage` and `Project` store projects and history in the browser. There is no server owner identity to authorize against. A submitted project ID or browser save is not ownership evidence.
- `ai/usage/track.ts` records provider usage and cached-token costs. Its logging intentionally tolerates persistence failure. `usage/store.ts` chooses Postgres or a local JSONL file; `usage/db.ts` can create/alter its tables on first access. None of these is an atomic spending reservation or a payment authorization service. This implementation never invoked those stores or accessed a database.
- `CallBudget` bounds calls and stops after already-reported costs. It cannot cap the cost of the next model call, enforce concurrency across workers, or replace durable accounting. Its resume counters now include earlier stages.
- `proxy.ts` blocks paid routes regardless of email. The new `/api/ai/staged-generation` handler independently returns 403 and has no provider import or environment enable flag. Existing historical routes still depend on the proxy: do not lift its blanket block to enable one new route.

## Proposed admission and execution

1. Use an established OpenID Connect provider with Authorization Code + PKCE and a server session library. For the private developer, provision one allowed **issuer + immutable subject ID** out of band. Verify issuer, audience, signature, expiry, nonce and OAuth state on the server; never authorize by a supplied email. Store an opaque random session ID as a hashed server record; use a Secure, HttpOnly, SameSite cookie, short expiry and revocation. Reject unverified, expired and non-allowlisted sessions before reading projects or constructing a provider. Validate Origin and a session-bound CSRF token for mutations. Verify the deployment's TLS and cookie behavior.
2. Introduce a server project row with `id`, `owner_subject`, revision and staged source. Import a browser project only after authentication, under the authenticated subject; the server creates the ownership assignment and a fresh project ID. Every create/read/advance/checkpoint/export/edit query is scoped by authenticated owner. Never accept checkpoints, model choice, prior usage, prices or budget limits from the client as authority.
3. In one database transaction, lock the project/run and the developer's budget row. Check revision, next stage, run state, daily cap, per-run cap and active-call count. Insert a unique idempotency key scoped to owner/run/stage. Reserve one call slot and the full worst-case call charge in integer microdollars. Allow only one active stage per run and one paid call per private user. Concurrent, duplicate, stale and over-limit requests must not create another call.
4. Fix the model, context/input token ceiling, output ceiling (currently 12,000), 170-second timeout and `maxRetries: 0` on the server. Reserve `input_token_ceiling × uncached_input_price + output_token_ceiling × output_price`, rounded upward; use a conservative verified tokenizer or documented provider input ceiling before sending anything. Bound serialised prior checkpoints as well as user text. Unknown prices, missing rates, oversized input or an unavailable budget database deny execution. One call per stage, five per run; no automatic corrective calls, SDK retries, polling retries or automatic restart. Derive the actual dollar caps from an explicitly approved private-user budget before enabling.
5. After the reservation transaction commits, execute exactly one stage through `advanceTerraPromptRun`. The Stage 3 response is a programme and room relationships; deterministic software solves its plan. The other stages use the existing slice contracts and deterministic compiler/validators. Do not call the one-shot scene generator. Complete work on the server independently of a browser disconnect; expose an authenticated status/read endpoint so a client can reconnect without resubmitting the model call.
6. Persist the call outcome, usage and candidate/checkpoint in a durable transaction before acknowledging acceptance. On success, atomically advance the project revision and accepted-stage pointer. On invalid geometry or provider failure, keep the last accepted pointer untouched and retain findings separately. A failed candidate scene must not be presented as an accepted building. Store the architectural source, component IDs, original prompt, immutable stage input, output and parent checkpoint hash for reproducibility; protect them by owner checks.
7. Settle the reservation using provider-reported input, cached input, output (including reported reasoning usage in the output total), provider request ID and the snapshotted pricing version. Record a unique call ID and stage/run/user linkage for both successful and unusable responses. Missing/unknown usage is **unknown**, never a zero-cost success: hold the full reservation pending reconciliation, block further calls and surface the uncertainty. A timeout or crash after dispatch must not release an unaccounted reservation or trigger an automatic retry. Reconcile with provider billing before manual resolution. The current tolerant usage logger may be a reporting mirror, not the authoritative ledger.
8. Save each accepted stage durably so refresh, worker restart, network loss and a later-stage failure retain completed work. Keep failed calls counted toward the run's five-call maximum. A server crash before dispatch can release a reservation only with evidence no call was sent; ambiguous dispatch remains reserved. Any manually approved restart is a new budgeted run, not a counter reset.

## Required activation evidence

Use isolated test databases and mocked providers first. Verify forged email/header, missing/expired/revoked sessions, wrong owner, cross-origin and missing CSRF rejection **at the route handler**; concurrent budget reservations; duplicate idempotency keys; revision conflict; five-call exhaustion; token ceilings; unknown-price refusal; recording invalid/truncated output usage; missing-usage hold; database failure; crashes before and after dispatch; disconnect/reconnect; restart after Stage 3; and accepted-checkpoint preservation. Verify a real sign-in round trip without paid work. Confirm migrations and owner policies in the intended private environment, then request explicit approval for one bounded live run and its maximum reserved charge.

Only after that evidence passes may one narrowly authenticated staged route be exempted from the proxy's paid-route block. The historical one-shot and admin routes stay blocked. This document is a specification; none of the session, ownership or reservation controls above is implemented or verified by the offline generation tests.
