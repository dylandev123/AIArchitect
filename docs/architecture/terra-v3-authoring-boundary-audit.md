Terra → V3 authoring boundary audit · 22 October 2026

**Verdict.** A smaller architectural input can feed the existing V3 scene reliably within a declared scope. The repository already demonstrates this for massing concepts and coordinated room subdivisions. Neither current compact contract preserves the entire expressive range of the existing V3 scene. The right direction is a disposable authoring adapter with concise architectural controls, optional exact geometry and explicit capability diagnostics, retaining V3 as the sole editable scene authority.

This is an audit of the current working tree, including existing uncommitted changes. No application source, flags, credentials or saved projects were changed, and no provider requests were made. Route behavior below is conditional on its flags; this audit does not establish which flags a deployed instance uses.

**Current paths matter.** There is no single Terra input contract:

| Path | What Terra supplies | Boundary and consequence |
| --- | --- | --- |
| Ordinary V3 generation, including advanced terrain | A scene-shaped response with named architecture and V3 semantic collections | Broad scene vocabulary and generic/proxy rendering remain available. This is a different acceptance contract from faithful blueprint construction. |
| New flat generation with `AI_V3_ARCHITECTURAL_BLUEPRINT=1` | One `v3-plan-first-1` response containing plan and exterior | Plan → massing → exterior are local stages of one response, with at most one narrow objective repair. The transmitted plan uses the canonical plan schema except for its relationship-based storeys. It does **not** use the complete compact-plan schema. |
| `/api/ai/plan`, with its evaluation flag | Compact 2D plan, then a separate exterior response on explicit elaboration | Derives more bookkeeping and permits deferred construction decisions. Invalid local intent can remain in an editable draft. A saved draft is not proof of constructibility. |
| `/api/ai/concept`, development plus explicit opt-in | Compact envelopes, storey heights, roof choices and rectangular outdoor spaces | Builds real V3 massing with no rooms, entrances or developed circulation. It is an isolated concept preview, not an integrated concept-to-complete-house pipeline. |

**1. Technical fields Terra authors, and what V3 can derive**

“Derive” needs three distinct meanings: compute an exact consequence, apply a disclosed editable default, or make a new architectural decision. Only the first is automatic without additional design authority.

| Field or obligation | Current state | Recommended ownership |
| --- | --- | --- |
| `transform.position/rotation/scale`, `dimensions`, vertical centre, array ordering | Named `architecture` already materializes these. Plan-first and concept inputs avoid them. Ordinary scene generation still exposes runtime geometry concerns. | V3 computes these exclusively for semantic architecture. They are compatibility data, not additional Terra decisions. |
| Total mass height, storey elevations, host roof x/z/yaw/width/depth/bearing level | Already computed by `lowerV3ArchitecturalBlueprint` from placement, plan and storey heights. | Keep derived. Storey heights and intentional base elevation remain architectural controls. |
| Building outline bounding envelope | Already measured for blueprint line/arc outlines, including exact arc extrema. Concept input still requires width/depth as well as an optional outline. Shaped outdoor features also require width/depth. | Derive bounds from exact outlines wherever those spans are merely redundant addressing envelopes. Preserve the local origin and segment identities; do not recenter or rescale the design. Articulated operations still need their placement envelope. |
| Roof IDs, generated route `surfaceId`, repeated entrance/program records, repeated role/character text | Compact-plan expansion already creates these when omitted. The full-property prompt still requires several of them because it starts from the canonical plan schema. | Reuse compact expansion consistently. Keep explicit user requirements and deliberate program allocations; an automatically generated building program record is not verification of the brief. Preserve supplied identities and reject ambiguous references. |
| Storey/room IDs | Compact input can allocate IDs; the advertised relationship-based storeys require room IDs for node references. | Derive unreferenced bookkeeping. Keep stable references for rooms used by topology, entries and adjacencies; avoid positional renaming on future edits. |
| Room `footprint:{x,z,width,depth}` | Legacy input authors each rectangle. Relationship-based layouts already compute them from ordered, weighted splits and functional regions. | Terra specifies topology, orientation, proportions and important size constraints; V3 calculates shared edges and rectangles. This is subdivision, not a general space-planning solver. Nonrectangular shells still need explicit rectangular functional regions. |
| Route endpoint world coordinates, owner bounds, route ribbons | Already derived from entrances, site-access points and local dry-surface contacts. | Keep derived. Route width/use and deliberate bends/curves remain architectural decisions. Automatic obstacle avoidance needs a new routing algorithm and must preserve the chosen arrival sequence. |
| Stair treads, riser count, flights, landings, slab cuts, guards and lift parts | Already built from host levels, reservation, type and direction. The compact plan can defer flight details to Terra’s exterior response. | Keep construction parts derived. Reservation, connected levels, handedness and intended arrival/exit orientation may affect architecture. A bounded flight fitter could choose among explicitly allowed options; it cannot silently enlarge or relocate a core. |
| `roof.thickness`, feature construction depths and small member sizes | Roof thickness is mandatory in the blueprint exterior; concept roof thickness is implicit. Feature height can be deferred, but Terra must later supply it. Several assembly thickness/size fields are already optional. | Use versioned schematic defaults with exact overrides. This is a construction policy, not a uniquely inferred answer. Retain explicit roof profile, pitch, eaves, visible member proportions and true occupied heights. |
| Pool/deck vertical arithmetic | Features use `baseElevation + height` as their top/rim datum. Terra currently coordinates these numbers. | Prefer explicit finished-surface/rim levels plus separate construction depth, lowered into the existing fields. A “flush” relation can derive one datum from another. Automatic excavation, drainage and infinity-edge design do not follow from that relation. |
| Door/glazing `start/end`, `heightRatio`, `sill`, `segmentId` | Terra chooses exact wall addresses and dimensions. Main-entry canopy geometry already has a small compiler expansion. | Add wall/room-relative opening placement with width, alignment and head/sill rules. V3 can calculate fractions once the wall, target room and placement rule are unambiguous. It cannot infer the intended entrance or facade composition from a style label alone. Preserve exact addresses as overrides. |
| Balcony/portico/shade `assemblies[].parts[]` | Terra decomposes assemblies into slabs, posts, beams and rails with local spans, depths, elevations and references. | High-value new compiler work: accept an architectural assembly with host, level, span, depth, access, support rhythm, guard edges and optional exact members. Generate repeated construction pieces. An assembly name or free-text `intent` currently does not construct it. |
| Partition `boundaryId`, door `offset`, partition/door references | Shared room boundaries already have deterministic IDs and geometry, but detailed blueprint authors must address them. | Accept “between room A/B, partition type, passage width/alignment”; derive the exact boundary and offset if unique. Wall location, privacy, aperture type and passage position remain architectural choices. Detailed partitions are currently deferred by default. |
| Explicit support relationships | Ordinary support can already be inferred on an effective, nonpersistent scene. | Derive ordinary unambiguous support. Preserve intentional cantilever, suspension, attachment and hosting choices. Geometry-only inference is best-effort, not structural engineering. |

Implementation evidence: [named geometry mapping](../../src/lib/v3/architecture.ts) (37–47), [semantic lowering](../../src/lib/v3/architecturalBlueprint.ts) (145–198), [input expansion](../../src/lib/v3/architecturalPlanAuthoring.ts) (70–123), [room development](../../src/lib/v3/roomLayout.ts), [route geometry](../../src/lib/v3/routeGeometry.ts), [circulation construction](../../src/lib/v3/circulation.ts), [assembly/opening fields](../../src/lib/v3/composition.ts) (14–49), [room boundary derivation](../../src/lib/v3/interior.ts) (181–240), [effective support](../../src/lib/v3/derivedSupport.ts).

The largest remaining authoring burden is not meshes: those are already generated. It is precise coordination across independent rectangles, wall addresses, vertical datums, route contacts and assembly members. Eliminating only runtime arrays will not address that burden.

**2. Architectural concepts Terra should express directly**

Terra should continue to make spatial decisions, including quantitative ones. Width, depth, height, orientation and exact curves can be architecture, not low-level construction bookkeeping.

| Direct architectural statement | Information it must retain | Geometry V3 should calculate |
| --- | --- | --- |
| Massing hierarchy and composition | Primary/secondary/connector roles, exact or proportioned envelope, placement, orientation, roof silhouette, supported setbacks | Storey datums, walls, slabs, roof bearing and tessellation |
| Solid/void and outdoor rooms | Court boundaries, which wings frame them, open side, terrace/deck extent, shade and outlook | Supported outlines, surface offsets and construction pieces; not invented holes |
| Arrival and movement | Site entry, destination entrance and served room, public/service separation, intended sequence, route width and optional exact course | Endpoint coordinates and ribbons; later a constrained route solver if implemented |
| Program, privacy and room organization | Uses, adjacencies, ordered functional zones, proportions, size constraints, explicit corridors and core reservations | Coordinated room datums and shared boundaries |
| Vertical experience | Storey heights, double-height intent, stairs/lifts, levels connected, roof access, thresholds and finished datums | Supported slab removal, flights, shafts and guards; partial atrium voids need new capability |
| Facade composition and climate response | View/private/service/arrival faces, opening rhythm, operable passage versus window, shade depth and support rhythm | Wall-relative aperture coordinates and shade/assembly members under declared rules |
| Material and tectonic character | Major finishes, visible roof edge, light/heavy members, glazing/frame character | Existing supported material parameters and component finish assignments |
| Obligations and uncertainty | Actual requested program, hard constraints, preferences, assumptions, deferred decisions, unsupported requirements | Validation diagnostics and provenance, without claiming the labels are built |

Some vocabulary already exists (`massHierarchy`, `facadeRoles`, `spaceHeight`, `mainEntry`, `serves`, estate relationships and requirements). It is not uniformly available across all authoring paths. Facade roles can generate preset openings in ordinary V3, while faithful blueprint approval rejects unchosen generated apertures. That prevents silent changes but means “view facade” alone is not currently sufficient for faithful exterior authoring. See [facade rules](../../src/lib/v3/composition.ts) and [construction-policy conflicts](../../src/lib/v3/architecturalBlueprint.ts) (110–142).

Qualitative claims also need an honest boundary: “ocean-facing,” “private,” “cross-ventilated,” “unobstructed view” and “luxurious” are design intentions, not guaranteed outcomes of compiling an object. Existing concept prompts ask Terra to review such claims; that is not an independent geometric view/privacy/climate evaluator.

**3. Can a small format preserve freedom and convert reliably?**

**Yes for explicitly supported designs; not yet as a universal replacement.** There are three separate questions:

- **Representability:** can the input retain every relevant design decision? Current concept input cannot represent many existing V3 decisions.
- **Deterministic conversion:** does an accepted, unambiguous input lower to the intended V3 geometry and survive editing/reload? Existing tests establish this for their fixtures and cases.
- **Natural Terra reliability:** does Terra consistently produce valid, architecturally good inputs from varied briefs? The offline proofs do not establish this, or demonstrate token/cost savings.

Concrete evidence from this audit:

- Concept tests build courtyard, L-shaped, pavilion, connected-wing and modest examples directly through `compileV3Scene`, with real walls/roofs and zero rooms. A retained concept reproduction preserves its U outline and polygon roof. Invalid outlines, roof combinations, skew connections and other diagnosed cases are refused without a replacement scene.
- Plan/blueprint tests preserve curved and articulated geometry through plan → massing → exterior, edits and JSON reload. Room-development tests cover changing proportions, rotated hosts, multiple storeys, upper setbacks and fixed stair/lift reservations. Hand-authored examples are capability demonstrations, not natural-generation success rates.
- The retained natural Terra plan reproduces **17 room warnings: 3 outside-host, 6 overlaps, 8 adjacency failures**. Its explicit coordinates are preserved. A separate coordination proposal reduces these to 9 warnings and retains ambiguity. This shows why automatic arithmetic helps, and why a general layout cannot be inferred merely from a list of adjacencies.
- `sameArchitecturalPlan`, construction-policy checks and component receipts protect declared geometry against drift and generic substitution. Receipts reuse component builders, so common builder defects remain possible; some outline checks are independent.
- Eight focused test files ran: **123 passed, 1 failed, 124 total**. The failure is the existing `terraFreedomAudit.test.ts:107` dispatch-count assertion: expected `{specialized:16,generic:14}`, observed `{specialized:17,generic:13}`. Its fallback-recovery test passes. This audit does not change that assertion or claim the suite is green; the count mismatch needs reconciliation before using that test as current freedom certification.

The two current compact formats introduce real restrictions:

- **Concept:** a closed set of roof/outdoor kinds; rectangular outdoor spaces; no complete estate access/program/room/facade/assembly/circulation authoring; low plinths only; limits on height/storey count and site dimensions. `conceptEnvelopeSignature` is a preservation helper exercised by tests, not an implemented room-development handoff. Concept roof values also differ from blueprint conventions: pitch is 1–60 even for a flat roof, while blueprint flat pitch must be zero. Integration needs an explicit normalization rule. Another semantic choice is hidden in the adapter: `outdoorSpaces.kind:"arrival"` lowers to `courtyard`, whose specialized builder constructs a perimeter ring. The concept input needs an explicit distinction if Terra intends a fully paved arrival surface.
- **Relationship room layout:** ordered axis-aligned slicing trees and rectangular functional regions, with limits of 100 regions and 300 nodes per layout. It is not a general graph-to-plan solver. Multiple regions can represent a nonslicing arrangement by giving each room its own explicit bounds; within those limits this can preserve existing valid nonoverlapping rectangular room geometry, but it brings back the independent-coordinate burden. Legacy exact rectangles also remain available to the parser. Polygonal/curved rooms are already outside the existing V3 room-datum model, not a new loss caused by subdivision. A reserve leaf means unallocated space, not a slab void.
- **Blueprint construction:** arbitrary semantic labels are accepted, but supported construction is narrower than the ordinary V3 scene. Unsupported feature boundaries may remain 2D reservations and then block elaboration. An unknown noun rendered as a generic box in ordinary V3 is not faithful implementation of the named feature. Blueprint receipts explicitly reject generic substitution for managed architecture.

Existing builder limits are separate from these input limits: outline holes, arbitrary independent per-storey outlines, splines, skew/curved Boolean mass junctions, domed roofs and partial floor voids are not solved by a smaller schema. Nonrectangular hosts support a narrower roof family set. The broader V3 runtime also has support/terrain/generic-object possibilities excluded by the flat blueprint and concept paths. “No sacrifice” must be evaluated against the chosen baseline, not assumed because both paths eventually produce `V3Scene`.

**Recommended contract and implementation order**

Use a concise architectural core: site and access; masses and exact/proportioned shapes; storeys; functional room organization; openings; circulation; outdoor spaces; architectural assemblies; finishes; requirements and assumptions. Natural-language concept/character remains explanatory. Its executable fields must retain the actual spatial decisions.

Provide structured semantic shortcuts **and** optional exact forms for supported geometry: line/arc boundaries, explicit room rectangles, exact aperture spans, deliberate route curves, core reservations and assembly parts. A shortcut must not prescribe a fixed house template. Exact inputs must not be forced back through a simplifying shortcut. Broader runtime features require explicit adapters or honest capability diagnostics; an unchecked raw-object escape hatch would bypass fidelity protection.

Convert once: validate authoring input → expand identities/defaults → resolve unambiguous geometry → existing V3 semantic plan/scene → existing preflight/compiler/receipt checks. Persist V3 as the editable geometry authority. Keep unresolved intent and derivation/default provenance as metadata; do not replay a successful authoring recipe over later manual edits.

1. **Remove existing redundant obligations first.** Bring full-property authoring into alignment with compact expansion, preserving the current plan’s optional concepts such as double-height and explicit requirement/program allocations. Do not simply swap schemas: the compact advertised input omits some canonical fields and has different default/deferred behavior.
2. **Add deterministic architectural assemblies and datum relations.** Start with explicit host-relative balconies/porches/shade and flush terrace/pool contacts. Generate members and arithmetic while preserving the chosen span, depth, access, support rhythm and visible proportions.
3. **Add room/wall-relative openings and partition addresses.** Require a unique host edge and rule; retain exact controls for exceptional arrangements. Keep route/stair fitting bounded by the approved spatial reservations.
4. **Keep exact room layouts available alongside subdivision.** Use subdivision where its topology is appropriate. A richer planner is a separate feature with explicit constraints and unresolved results, not a hidden packing heuristic.
5. **Prove coverage before replacing a path.** Compare canonical semantic geometry and meaningful construction output across representative existing curved, concave, classical, modest, multi-storey and estate fixtures, including exact overrides. Check stable references, unchanged input, repeatability, rotation/local-frame behavior, editing/reload and failure without substitution. Independently verify claimed passages/courts/views where those claims matter. Then evaluate natural Terra outputs with retained first responses and measured failures, sizes and usage.

The architectural boundary should be: **Terra chooses spaces, forms, relationships, proportions and architectural expression; V3 resolves their coordinates and construction under explicit rules.** A compact format can make that boundary much clearer. Today’s repository proves useful parts of the conversion, not unrestricted architectural freedom or general natural-author reliability.
