# Terra development versus redesign audit

The demonstrated bottleneck was conflicting **edit-scope instructions**, followed by the model choosing to preserve the composition. The retained response contains no attempted structural redesign. The operation contract and executor can execute substantial architectural replacement without a new engine. This establishes permission and execution capability; improved independent Terra design behavior still requires a controlled live comparison.

No live OpenAI calls were made for this audit. No keys were loaded, knowledge approvals changed, database migrations run, commits made or deployment performed. Existing unrelated working-tree changes were left in place.

## Retained evidence and findings

All call evidence is in [the original retained experiment](../property-value-development/REPORT.md). The new [machine-readable audit](retained-call-audit.json) records hashes, exact request text, actual usage, raw-provider contract, unchanged operation comparison and model decisions. It distinguishes the historical request from the newly changed request builder.

1. **Authorization was partial and contradictory.** The exact [request](../property-value-development/request.json) said “Prioritize meaningful massing improvements when needed” and “Massing revision is authorized.” However, the wrapper also required development “with the existing spatial hierarchy,” “Do not replace the house,” and “Preserve the existing residence rather than generating a replacement.” It did not clearly authorize replacement/reorganization of existing floors, walls, roofs and volumes. The model had permission to revise massing in principle, coupled with explicit composition-preservation language.
2. **Ordinary edit policy reinforced conservation.** The exact [retained system](../property-value-development/settings.json) ended its operation instructions with “Preserve unrelated elements and IDs during edits; use only targeted operations.” Its design guide also applied architectural principles within scoped edits while preserving unrelated architecture. The knowledge preamble described a scoped edit preserving unrelated geometry and programme. Preserving unrelated work is appropriate; combining this policy with “Do not replace the house” and existing-hierarchy language made the intended redesign scope ambiguous. This is evidence of instruction pressure, not proof of an inaccessible internal reasoning process.
3. **The operation schema did not cap this at nine.** The actual provider response retains its JSON schema at `text.format.schema`: `operations.maxItems` is **800**, and alternatives include add, replace, remove, move, rotate, resize, finish, attach, place-on and set-terrain. Existing elements were not immutable in that contract. The local scene limit is **400 elements**; the baseline had 77 and the result 83. No minimum-operation target is appropriate. Replacement must keep the addressed ID; genuinely new elements may receive new IDs. Attachment chains must exist and be acyclic; wall openings must fit; final support/facade/railing relationships must remain valid. These require coordinated transactions, not architectural conservation. The executor checks the completed transaction, so dependent geometry can change together.
4. **Nothing larger was discarded from the visible response.** Parsing the raw provider message yields exactly the same nine operations as the saved SDK output and operations artifact. The raw status is `completed`, error and incomplete details are null, truncation is `disabled`, SDK finish reason is `stop`, HTTP status is 200 and the transport records one call. All nine operations were accepted atomically. There is no retained visible larger plan, rejected extra operation, local operation filter, repair or omitted batch. Reasoning content is encrypted/empty in the retained response and cannot establish what the model considered privately.
5. **New property-value knowledge had no live influence.** The retrieval context inferred `$25m` and `property-value-25m-50m`, but this proposed profile was not among the selected recipes. Approval filtering excluded it. The four actual selections were `facade-materials`, `estate-composition`, `roof-main-secondary`, and `waterfront-estate`, under the scoped budget of four entries / 6,500 characters. Each received a model design decision. The model linked facade materials to the bronze door/screens and waterfront sequence to the new terrace threshold; it explicitly described estate composition and roof hierarchy as retained. Some citations refer to inherited geometry and some omit required kinds, so citations show declared use, not verified causal influence or architectural completeness. The recipes' suggested operation lists were additive, but are contextual guidance rather than a schema allowlist; replace/move/resize were actually returned and accepted.
6. **17,039 is total token usage, not 17,039 tokens of construction.** The provider records **12,681 input + 4,358 output**, with **2,588 reasoning tokens included within output**, leaving **1,770 non-reasoning output tokens**. Input includes the system/design guide, retrieved knowledge, complete 77-element scene, request, any reviewed lessons and structured-output schema. Exact per-input-component token attribution was not retained. The output allowance was **30,000**, well above actual output, and the response stopped normally. The visible model summary explicitly chose a targeted revision preserving “Existing primary massing, roofs…”; its plan likewise says the composition is preserved. The evidence supports a conservative design choice under contradictory scope instructions, not token exhaustion or an executor quota.

## Targeted changes

- The existing edit request now accepts optional `editIntent: refine | redesign`. Omission retains conservative behavior. Generation and the existing scene-operation/result schemas remain unchanged.
- The canonical route appends explicit mode-specific system instructions. **Refine** preserves composition and applies targeted work. **Redesign** explicitly permits replacing, removing, moving, resizing and reorganizing inadequate floors, enclosure, roofs, entrances, facades and volumes, with all dependent geometry coordinated atomically. It overrides composition-preservation instructions only within the requested architecture; unrelated site geometry, terrain and project data remain protected by the existing scope instructions. Budgets, attachment validation and geometric checks are unchanged.
- The development-request helper now produces an unambiguous Refine or Redesign request. The existing opt-in `recompose: true` maps to Redesign; it no longer combines massing authorization with “Do not replace the house.” An explicit `intent` takes precedence.
- The normal direct-scene studio exposes **Refine** and **Redesign** buttons using the same endpoint and executor. Successful project redesigns append an `Architectural redesign` version using existing history; the original remains available to Undo/restore and persists with the project. Existing concurrent-change checks still prevent stale responses from being applied. The playground continues to use its existing local undo stack; persistent version-history verification below covers normal projects.

No replacement-house generator, new operation type, architectural template, migration, relaxed geometry gate or separate building engine was introduced. Ordinary refinement remains an instruction-scoped edit as before; this change does not introduce a new deterministic scope-enforcement system.

## Remaining capabilities and next experiment

The system still represents rectangular parts and flat/gable/hip roofs, plus the approved open curved pavilion. Arbitrary polygonal/curved solids, arbitrary roof geometry and mesh/CSG are unsupported. There is no automatic stair/interior/service-system design, comprehensive circulation verification, engineering, drainage, waterproofing, code validation or valuation model. Manual supported steps/landings can be authored with primitives, but upper-room access must be proved or disclosed. The stronger offline studies retain unresolved programme/access questions. Passing relationships is not a quality or luxury certificate.

**One controlled live redesign test is justified, but has not been performed or authorized by this work.** Use the same retained baseline and an explicit main-house Redesign brief, preserve pool/pavilion/site data, retain exact system/request/schema/retrieval/raw response/usage, disable retries, and execute one atomic transaction. Judge changed primary floors/enclosure/roof hierarchy and arrival sequence in matched views, rather than operation count alone. Verify retained IDs, unrelated site geometry, Undo and reload before accepting the candidate. Keep proposed value recipes excluded unless separately approved; otherwise that experiment cannot establish their influence. If the model again returns only secondary decoration, the remaining problem would be model planning/choice despite explicit permission, which this offline audit cannot resolve.
