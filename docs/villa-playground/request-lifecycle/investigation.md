## Evidence and limits

The route exported `maxDuration = 180`; Next's installed documentation says deployment platforms use that value, so it is not proof of a local development-server timeout.
- For the main Villa path, the unprefixed “Fetch is aborted” phrase is consistent with the browser fetch/response-body catch; provider exceptions are wrapped by the route rather than forwarded verbatim. The browser displayed raw `Error.message` for an `AbortError`, which could expose “Fetch is aborted” without saying whether fetch failed before headers or while consuming JSON. The route also coupled browser disconnection to cancellation of an already dispatched paid provider call. Those are demonstrated lifecycle defects, independent of architecture.
- `.next/dev/trace` contains three completed `/api/ai/villa` requests in the retained session, starting at 12:02:02, 12:07:02, and 12:40:56 Saint Lucia time (UTC−04:00). Durations: 65.633 s, 63.546 s, and 18.780 s. The corresponding last generation artifact was written at 12:41:15.502.

## Fix

- Preserve the existing 160-second provider bound and 180-second route budget. Give main Villa clients 195 seconds, leaving room to receive classified server errors. The visual-review provider keeps its own existing deadline.
- After provider dispatch, a browser disconnect no longer cancels the provider. One bounded generation may finish and incur usage; no automatic retry is allowed. Requests already cancelled before dispatch make zero provider calls.
- A browser-generated UUID is persisted locally before POST. The server exclusively claims it before any paid call; duplicate IDs read the existing status rather than dispatch again. All usage records now carry this operation ID.
- Retain original response text before SDK output validation as before. Also correlate provider completion, usage, provider request ID, elapsed time, and browser disconnection with request/generation artifacts. Provider, SDK, timeout, local processing, and architecture failures remain distinct. Unknown usage is explicitly marked unknown.
- Atomically retain the full validated response (including the resolved configuration for edits and locally assembled components) before delivery. GET recovery and the “Recover last Terra response” button never invoke the provider. Failures do not replace the current villa. A process interrupted before completion leaves a pending record; recovery does not silently buy another attempt.
- If request-claim storage is unavailable initially, return 503 with zero calls. If raw diagnostic retention alone fails, accepted configurations still work. If final retention fails after provider completion, report `recoveryRetained: false`; process survival and writable local disk are required for durable recovery. This development-only filesystem mechanism is not a hosted job queue and cannot keep computation running through a server restart.
